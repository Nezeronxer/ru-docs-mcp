# OrangeData

## Тело POST подписывается SHA256-RSA в X-Signature, GET статуса подписи не требует
Любой запрос на отправку данных (создание чека) подписывается: SHA256-RSA 2048 бит, паддинг PKCS1 (в примерах
`RSA::SIGNATURE_PKCS1` и `RSASignaturePadding.Pkcs1`), результат в base64 в заголовке `X-Signature`. В примере
подписывается та же строка JSON, что уходит в теле (php: `json_encode(..., JSON_UNESCAPED_UNICODE)`). Для
`GET .../status/...` подпись не нужна. Поле `key` в теле - название ключа проверки подписи; у выпустивших сертификат
после 01.02.2025 это `ИНН_ID`. Ошибка подписи даёт 400, неверный клиентский сертификат (mTLS) даёт 401.
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05

## id чека уникален в организации: повтор POST даёт 409, не дубль
`id` (1-64 символа) должен быть уникален в рамках организации. Повторный POST с тем же `id` вернёт
`409 Conflict` с пустым телом: чек уже создан, ждите его статус, а не шлите заново. `201 Created` значит
только "добавлен в очередь". При `503` очередь переполнена: повторить после паузы из заголовка
`Retry-After`. При сетевой ошибке документ советуют отправлять повторно с таймаутом (пример: 5 попыток с
интервалом 10-20 секунд).
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05

## Чек создаётся асинхронно: результат только через GET status (или callbackUrl)
После `201` чек ещё не пробит. Состояние: `GET /api/v2/documents/{inn}/status/{document_id}`. `202` - в
очереди, `200` - обработан (тело с `fp`, `fsNumber` и т.д.), `422` - не прошла проверка кода маркировки,
`524` - не успели обработать, надо отправить чек с НОВЫМ `id`, `400` - чек или организация не найдены.
Необязательный `callbackUrl` получает результат POST-ом. Запрос, пролежавший в очереди более 30
календарных дней, не выполняется.
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05

## Для ФФД 1.2 нужны ffdVersion: 4 и группа с суффиксом _2
`ffdVersion` по умолчанию `2` (ФФД 1.05), для ФФД 1.2 его обязательно передавать как `4`. Группы касс,
работающие с ФФД 1.2, имеют суффикс `_2` (`Main` -> `Main_2`, `Vend` -> `Vend_2`, `Transp` ->
`Transp_2`). Если `group` не указан или `null`, берётся группа по умолчанию. Актуальные имена групп
смотрите в личном кабинете.
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05

## НДС: tax в позициях и vatNSum в чеке нумеруются по-разному, с 2026 года 20% стало 22%
В позиции `tax`: 1 = 20% (22% с 01.01.2026), 3 = 20/120 (22/122 с 01.01.2026), 5 = 0%, 6 = без НДС. В
чеке нумерация иная: `vat3Sum` = 0%, `vat5Sum` = расчётная 20/120 (22/122 с 01.01.2026), `vat1Sum` = 20%
(22%). Не переносите номера из `tax` в `vatNSum`. Для возвратов за 2025 год есть флаг `useTax20`. Для
`tax` 5 и 6 `taxSum` в позиции игнорируется.
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05

## Текст чека перекодируется в CP866: неподдерживаемые символы молча пропадают
API принимает UTF-8, но фискальные накопители работают только с CP866, и символы вне CP866 отбрасываются
без ошибки (например, "Сок «Мечта»" станет "Сок Мечта"). Размер документа в ФН ограничен 32768 байтами
(около 250 позиций); сверх лимита ФН отклонит чек, рекомендуют не более 250 позиций.
Источник: https://raw.githubusercontent.com/orangedata-official/API/master/orangedata_API_Russian_ffd_1.2.pdf
Проверено: 2026-10-05
