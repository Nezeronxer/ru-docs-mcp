# Битрикс24 REST API

## Два разных лимита: 503 QUERY_LIMIT_EXCEEDED по частоте и 429 OPERATION_TIME_LIMIT по времени метода
Частота (leaky bucket): при превышении порога `X` приходит `503` и `QUERY_LIMIT_EXCEEDED`; счётчик падает на `Y` в
секунду. Энтерпрайз: `Y`=5, `X`=250; прочие тарифы: `Y`=2, `X`=50. Приложения с одного IP к одному Битрикс24 делят лимит.
Отдельно считается время выполнения метода: `429` и `OPERATION_TIME_LIMIT` блокируют только этот метод для
приложения или вебхука, первую повторную попытку планируйте по `time.operating_reset_at`.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/performance/limits.md
Проверено: 2026-10-05

## batch всегда отвечает 200: ошибки подзапросов ищите в result_error
Общей ошибки на пакет нет: статус `200`, упавшие подзапросы лежат в `result_error` по ключу подзапроса, успешные - в
`result`. В пакете не более 50 подзапросов, лишние получают `ERROR_BATCH_LENGTH_EXCEEDED`.
`halt=0` выполняет все подзапросы, `halt=1` прерывает цепочку на первой ошибке: для связанных вызовов
(`$result[ключ][поле]`) ставьте `halt=1`.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/how-to-call-rest-api/batch.md
Проверено: 2026-10-05

## Страница - до 50 записей; для больших выборок вместо start += 50 берите start=-1 и фильтр по >id
При `start >= 0` Битрикс24 ещё и считает `total`, на больших выборках или сложных фильтрах это медленно.
Для выгрузки: сортировка по `id` по возрастанию, фильтр `>id` с последним полученным `id`, `start=-1`; цикл
идёт, пока метод не вернёт меньше 50 элементов. Поле `next` в таком цикле не используется.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/performance/huge-data.md
Проверено: 2026-10-05

## OAuth: access_token живёт 1 час, refresh_token - 180 дней, новый refresh_token сохраняйте вместо прежнего
Обновляйте токены, когда пришёл `expired_token` со статусом `401`, и повторяйте вызов с теми же параметрами.
Не обновляйте перед каждым запросом и не по расписанию (раз в час или в сутки): сервер авторизации создаст
нагрузку, и приложение может быть заблокировано автоматикой.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/oauth/auto-renewal.md
Проверено: 2026-10-05

## События подтверждаются только auth.application_token; без совпадения отвечайте 403
Для приложения сохраните токен из `ONAPPINSTALL` и обновляйте его в `ONAPPUPDATE`; для исходящего вебхука - из
поля *Токен приложения* его формы. Ищите сохранённый токен по `auth.member_id`. В `ONAPPUNINSTALL` данных
авторизации нет, и сравнение токена - единственная проверка, что вызвал Битрикс24.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/api-reference/events/safe-event-handlers.md
Проверено: 2026-10-05

## События не повторяются, а в исходящий вебхук не приходят OAuth-токены
Обработчик получает `POST` с `application/x-www-form-urlencoded`, все значения - строки. Если обработчик не ответил
или вернул ошибку, событие повторно не отправляется; для событий без потерь есть офлайн-события.
В исходящий вебхук приходят только `domain`, `client_endpoint`, `server_endpoint`, `member_id`, `application_token`.
`event.bind` работает только в контексте приложения, через вебхук будет `WRONG_AUTH_TYPE`.
Источник: https://github.com/bitrix-tools/b24-rest-docs/blob/main/api-reference/events/index.md
Проверено: 2026-10-05
